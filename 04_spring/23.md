<h1>Teste de Software com JUnit 5 - Teste da Classe Controller</h1>

<br />

Vamos avançar na criação dos testes estruturando três classes fundamentais para organizar e facilitar a implementação dos testes automatizados:

- A **classe utilitária `TestBuilder`**, responsável por centralizar a criação de objetos utilizados nos testes com dados simulados, evitando repetição de código e promovendo maior **reutilização, padronização e organização** na construção dos cenários de teste;
- A **classe utilitária `JwtHelper`**, responsável por auxiliar na geração e manipulação de tokens **JWT** durante os testes, permitindo simular cenários autenticados e validar endpoints protegidos da aplicação;
- A **classe de testes `UsuarioControllerTest`**, responsável por validar automaticamente o comportamento dos endpoints do recurso **Usuario** na camada de **controller**, verificando se as requisições e respostas da API estão funcionando conforme o esperado.

Com essa estrutura, os testes ficam mais organizados, legíveis e fáceis de manter, além de promover uma melhor separação de responsabilidades. A utilização de classes auxiliares reduz a duplicação de código e torna a criação de novos cenários de teste mais rápida e eficiente durante o desenvolvimento da aplicação.

<h2>👣Passo 01 - Criar a Classe Utilitária TestBuilder</h2>



A classe **`TestBuilder`** é uma classe utilitária criada para facilitar a construção de objetos utilizados nos testes automatizados, especialmente as classes **Model** relacionadas ao recurso **Usuário**.

Ela disponibiliza métodos estáticos responsáveis por criar e configurar objetos de teste com dados previamente definidos, evitando a repetição de código e tornando os testes mais organizados, legíveis e fáceis de manter.

No exemplo abaixo, a classe possui dois métodos principais:

- **`criarUsuario(Long id, String nome, String usuario, String senha)`** — cria e retorna uma instância da classe **`Usuario`** com os atributos preenchidos, incluindo a definição de uma foto padrão para os cenários de teste;
- **`criarUsuarioLogin(String usuario, String senha)`** — cria e retorna uma instância da classe **`UsuarioLogin`**, configurada com os dados necessários para simular uma autenticação no sistema.

Essa abordagem permite reutilizar facilmente objetos de teste em diferentes cenários, reduzindo a duplicação de código e facilitando a evolução da suíte de testes. Além disso, novos métodos podem ser adicionados à classe **`TestBuilder`** conforme novos recursos e classes **Model** forem implementados na aplicação.

	}

<h2>👣Passo 02 - Criar a Classe Utilitária JwtHelper</h2>



A classe **`JwtHelper`** é uma classe utilitária criada para facilitar o gerenciamento de tokens **JWT** durante os testes de integração, principalmente em conjunto com o **`TestRestTemplate`** do Spring Boot.

Ela disponibiliza métodos estáticos que encapsulam a lógica necessária para realizar autenticações, obter tokens e criar requisições HTTP autenticadas. Dessa forma, os testes ficam mais simples, organizados e fáceis de manter, evitando a repetição de código relacionado ao processo de autenticação.

No exemplo abaixo, a classe apresenta três métodos principais:

- **`obterToken(TestRestTemplate testRestTemplate, String usuario, String senha)`** — realiza uma requisição **POST** para o endpoint `/usuarios/logar`, simulando o processo de login da aplicação. O método envia as credenciais informadas e retorna o token JWT recebido na resposta. Caso as credenciais sejam inválidas ou a autenticação falhe, uma exceção é lançada para indicar o erro durante o teste.
- **`criarRequisicaoComToken(T body, String token)`** — cria um objeto **`HttpEntity<T>`** contendo o corpo da requisição e adiciona o token JWT no cabeçalho **`Authorization`** utilizando o padrão **Bearer Token**. Esse método é utilizado em requisições autenticadas que enviam dados no corpo, como operações **POST** e **PUT**.
- **`criarRequisicaoComToken(String token)`** — cria uma versão da requisição autenticada sem corpo, retornando um **`HttpEntity<Void>`** contendo apenas o cabeçalho com o token JWT. É utilizada principalmente em chamadas que não enviam dados, como operações **GET** e **DELETE**.

Essa abordagem permite centralizar a lógica de autenticação utilizada nos testes, promovendo maior reutilização de código e facilitando a criação de novos cenários de teste envolvendo endpoints protegidos por autenticação JWT.

<br />

### Classes e conceitos do Spring Framework utilizados nos testes

Para criar, enviar e validar as requisições e respostas HTTP durante os testes, utilizamos classes e recursos fornecidos pelo **Spring Framework**. Essas ferramentas permitem testar o comportamento dos endpoints da aplicação de forma semelhante ao consumo realizado por um cliente externo.

| Classe / Método / Conceito        | Descrição                                                    |
| --------------------------------- | ------------------------------------------------------------ |
| **`TestRestTemplate`**            | Cliente HTTP fornecido pelo Spring Boot para testes de integração, permitindo enviar requisições REST aos endpoints da aplicação. |
| **`HttpEntity<T>`**               | Representa uma requisição HTTP contendo o corpo (`body`) e os cabeçalhos (`headers`) que serão enviados ao servidor. |
| **`ResponseEntity<T>`**           | Representa a resposta HTTP recebida da aplicação, contendo o corpo da resposta, cabeçalhos e código de status HTTP. |
| **`HttpHeaders`**                 | Classe responsável pelo gerenciamento dos cabeçalhos HTTP, utilizada para adicionar informações como o token JWT no campo `Authorization`. |
| **`HttpMethod`**                  | Enumeração que representa os métodos HTTP disponíveis, como `GET`, `POST`, `PUT` e `DELETE`. |
| **`TestRestTemplate.exchange()`** | Método utilizado para executar requisições HTTP personalizadas, permitindo informar a URL, método HTTP, entidade da requisição e o tipo esperado da resposta. |
| **`Bearer Token`**                | Padrão utilizado para envio de tokens JWT no cabeçalho `Authorization`, permitindo que a aplicação identifique e valide o usuário autenticado. |

Com essa estrutura, os testes conseguem simular um fluxo real de utilização da API, incluindo autenticação, envio de dados e acesso a recursos protegidos, garantindo maior confiabilidade no comportamento da aplicação.

1. No lado esquerdo superior, na Guia **Package Explorer**, clique com o botão direito do mouse sobre a Package **com.generation.blogpessoal.util**, na Source Folder **src/test/java** e clique na opção  **New 🡪 Class**.

```java
package com.generation.blogpessoal.util;

import org.springframework.boot.test.web.client.TestRestTemplate;
import org.springframework.http.HttpEntity;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpMethod;
import org.springframework.http.ResponseEntity;

import com.generation.blogpessoal.model.UsuarioLogin;

public class JwtHelper {
    
    private JwtHelper() {}
    
    public static String obterToken(TestRestTemplate testRestTemplate, String email, String senha) {
        UsuarioLogin login = TestBuilder.criarUsuarioLogin(email, senha);
        HttpEntity<UsuarioLogin> request = new HttpEntity<>(login);
        
        ResponseEntity<UsuarioLogin> response = testRestTemplate
            .exchange("/usuarios/logar", HttpMethod.POST, request, UsuarioLogin.class);
        
        UsuarioLogin body = response.getBody();
        if (body != null && body.getToken() != null) {
            return body.getToken();
        }
        
        throw new RuntimeException("Falha no login: " + email);
    }
    
    public static <T> HttpEntity<T> criarRequisicaoComToken(T body, String token) {
        HttpHeaders headers = new HttpHeaders();
        String tokenLimpo = token.startsWith("Bearer ") ? token.substring(7) : token;
        headers.setBearerAuth(tokenLimpo);
        return new HttpEntity<>(body, headers);
    }
    
    public static HttpEntity<Void> criarRequisicaoComToken(String token) {
        return criarRequisicaoComToken(null, token);
    }
}
```

**Linha 30:** Início do método genérico público e estático `criarRequisicaoComToken`, que utiliza **Generics (`<T>`)** para permitir o recebimento de diferentes tipos de objetos no corpo da requisição. O método recebe um corpo genérico e um token JWT, retornando uma entidade HTTP (`HttpEntity<T>`) contendo o corpo da requisição e o token configurado no cabeçalho. Esse método é ideal para criar requisições que enviam dados, como **POST** e **PUT**, pois permite reutilizar a mesma implementação para diferentes classes Model.

- O **primeiro `<T>`** define um tipo genérico para o método, permitindo que ele receba diferentes tipos de objetos no corpo da requisição sem a necessidade de criar um método específico para cada entidade da aplicação. Dessa forma, o mesmo método pode ser reutilizado para classes como `Usuario`, `Postagem`, `Produto` ou qualquer outro objeto que precise ser enviado em uma requisição HTTP autenticada.
- O **segundo `<T>`** define o tipo do objeto armazenado dentro do `HttpEntity`, indicando qual será o tipo do corpo (`body`) da requisição HTTP retornada pelo método. Dessa forma, o `HttpEntity` mantém a tipagem correta do objeto recebido, garantindo maior segurança durante a implementação e permitindo que o método retorne uma entidade HTTP compatível com diferentes classes da aplicação.
- O **parâmetro `T body`** representa o objeto genérico que será inserido no corpo (`body`) da requisição HTTP. Como o tipo é definido utilizando Generics, esse objeto pode ser de qualquer classe da aplicação, como `Usuario`, `Postagem` ou `Produto`, permitindo reutilizar o mesmo método para diferentes entidades sem a necessidade de criar implementações específicas para cada uma.

**Linha 31:** Cria um objeto `HttpHeaders`, responsável por armazenar e configurar os cabeçalhos HTTP que serão enviados junto com a requisição.

**Linha 32:** Verifica se o token recebido já possui o prefixo `"Bearer "`. Caso possua, remove esse trecho utilizando o método `substring(7)`, armazenando apenas o valor do token JWT na variável `tokenLimpo` (somente a parte criptografada). Essa etapa evita a duplicação do prefixo no cabeçalho `Authorization`.

**Linha 33:** Define o cabeçalho `Authorization` utilizando o método `setBearerAuth`, adicionando automaticamente o prefixo **Bearer** ao token JWT no formato esperado pelo protocolo de autenticação.

**Linha 34:** Retorna uma nova instância de `HttpEntity<T>`, contendo o corpo da requisição (`body`) e os cabeçalhos HTTP configurados (`headers`). Esse objeto será utilizado pelo `TestRestTemplate` para enviar requisições autenticadas aos endpoints protegidos da aplicação.

**Linha 37:** Início do método público e estático `criarRequisicaoComToken`, que recebe apenas o token JWT e retorna uma entidade HTTP sem corpo (`HttpEntity<Void>`). Esse método é utilizado em requisições que não enviam dados no corpo, como operações **GET** e **DELETE**.

**Linha 38:** Chama o método genérico `criarRequisicaoComToken`, passando `null` como corpo da requisição e o token recebido como parâmetro. Dessa forma, o método reaproveita toda a lógica de configuração dos cabeçalhos HTTP do método `criarRequisicaoComToken` e evita a duplicação de código. Como não existe corpo na requisição, o retorno é definido como `HttpEntity<Void>`.

**Linha 30:** A anotação **`@SpringBootTest`** indica que a classe **`UsuarioControllerTest`** é uma classe de teste de integração que inicializa todo o contexto da aplicação Spring Boot. Dessa forma, todos os componentes configurados no projeto, como **Controllers**, **Services**, **Repositories**, configurações de segurança e banco de dados de teste, ficam disponíveis durante a execução dos testes.

A propriedade **`webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT`** configura a inicialização do servidor embutido em uma porta aleatória. Essa configuração permite que os testes realizem chamadas HTTP reais contra a aplicação, evitando conflitos com outras aplicações que possam utilizar a porta padrão do Spring Boot, geralmente a **8080**.

**Linha 31:** A anotação **`@AutoConfigureTestRestTemplate`** configura automaticamente a classe **`TestRestTemplate`**, permitindo realizar requisições HTTP para os endpoints da aplicação durante os testes de integração. Com ela, é possível simular o comportamento de um cliente externo consumindo a API REST.

**Linha 32:** A anotação **`@TestInstance(TestInstance.Lifecycle.PER_CLASS)`** define que será criada apenas uma instância da classe de teste para todos os métodos executados. Essa configuração permite utilizar métodos anotados com **`@BeforeAll`** sem a necessidade de declarar o método como `static`, facilitando a inicialização de dados compartilhados entre os testes.

**Linha 33:** A anotação **`@TestMethodOrder(MethodOrderer.DisplayName.class)`** define que a ordem de execução dos testes será baseada no nome informado na anotação **`@DisplayName`** de cada método. Essa organização permite controlar a sequência dos testes e facilita a leitura dos resultados apresentados durante a execução.

**Linhas 36 a 43:** Utiliza-se a anotação **`@Autowired`** para realizar a injeção automática das dependências necessárias para execução dos testes:

- **`TestRestTemplate`** — cliente HTTP utilizado para enviar requisições REST aos endpoints da aplicação e validar as respostas retornadas pelo servidor.
- **`UsuarioService`** — camada de serviço utilizada para realizar operações diretamente na lógica de negócio, como o cadastro inicial do usuário administrador. Seu uso garante que as regras da aplicação sejam respeitadas, incluindo o processo de criptografia da senha.
- **`UsuarioRepository`** — responsável pelo acesso direto ao banco de dados de testes, permitindo executar operações como exclusão dos registros antes da execução dos testes, garantindo um ambiente limpo e previsível.

**Linhas 45 a 47:** São declaradas constantes utilizadas como configurações dos testes:

- **`BASE_URL`** — representa o caminho base do recurso **Usuário** utilizado nas requisições HTTP realizadas durante os testes.
- **`USUARIO_ADMIN`** — armazena o e-mail do usuário administrador utilizado para realizar a autenticação nos testes. Esse usuário é criado no método **`@BeforeAll`** e posteriormente utilizado para obter o token JWT.
- **`SENHA_ADMIN`** — contém a senha do usuário administrador utilizado no processo de autenticação. Esse valor é utilizado em conjunto com o e-mail para gerar o token JWT necessário nos testes de endpoints protegidos.

**Linha 49:** Declara a variável **`token`**, responsável por armazenar o token JWT gerado após a autenticação do usuário administrador. Esse token será reutilizado nos testes que acessam endpoints protegidos da aplicação, sendo enviado no cabeçalho **`Authorization`** das requisições HTTP no formato **Bearer Token**.

**Linhas 51 a 56:** O método **`start()`**, anotado com **`@BeforeAll`**, é executado automaticamente uma única vez antes da execução de todos os testes da classe. Seu objetivo é preparar o ambiente inicial necessário para a execução dos cenários de teste, garantindo que exista um usuário autenticado disponível para os testes que acessam endpoints protegidos.

- Executa o método **`deleteAll()`** do **`usuarioRepository`** para remover todos os registros existentes na tabela de usuários do banco de dados de testes. Essa limpeza garante que os testes sejam executados em um ambiente previsível, evitando interferências de dados criados por execuções anteriores.
- Cria um usuário administrador utilizando o método **`criarUsuario()`** da classe utilitária **`TestBuilder`**, informando os dados necessários como nome, e-mail e senha. <h3>2.1. Metodologia de Testes Given-When-Then</h3>



A abordagem **Given-When-Then**, derivada da prática de BDD (Behavior-Driven Development), é utilizada neste projeto para estruturar os testes de forma mais semântica. Ela ajuda a descrever o comportamento esperado de forma legível:

- **Given** (Dado que): prepara o cenário de teste;
- **When** (Quando): executa a ação principal;
- **Then** (Então): verifica o resultado esperado.

A adoção dessa metodologia traz diversos benefícios, entre eles:

- **Melhor organização dos testes**, tornando o fluxo mais claro e compreensível.
- **Facilidade na identificação de falhas**, pois explicita de forma objetiva **o que foi feito**, **em qual contexto** e **qual era o resultado esperado**.

package com.generation.blogpessoal.controller;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotNull;
import static org.junit.jupiter.api.Assertions.assertNull;

import java.util.Optional;

import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.MethodOrderer;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.TestInstance;
import org.junit.jupiter.api.TestMethodOrder;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.resttestclient.TestRestTemplate;
import org.springframework.boot.resttestclient.autoconfigure.AutoConfigureTestRestTemplate;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.http.HttpEntity;
import org.springframework.http.HttpMethod;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;

import com.generation.blogpessoal.model.Usuario;
import com.generation.blogpessoal.repository.UsuarioRepository;
import com.generation.blogpessoal.service.UsuarioService;
import com.generation.blogpessoal.util.JwtHelper;
import com.generation.blogpessoal.util.TestBuilder;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureTestRestTemplate
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
@TestMethodOrder(MethodOrderer.DisplayName.class)
public class UsuarioControllerTest {

	@Autowired
	private TestRestTemplate testRestTemplate;

	@Autowired
	private UsuarioService usuarioService;

	@Autowired
	private UsuarioRepository usuarioRepository;

	private static final String BASE_URL = "/usuarios";
	private static final String USUARIO_ADMIN = "root@root.com";
	private static final String SENHA_ADMIN = "rootroot";

	private String token;

	@BeforeAll
	void start() {
		usuarioRepository.deleteAll();
		usuarioService.cadastrarUsuario(TestBuilder.criarUsuario(null, "Root", USUARIO_ADMIN, SENHA_ADMIN));
		token = JwtHelper.obterToken(testRestTemplate, USUARIO_ADMIN, SENHA_ADMIN);
	}

	@Test
	@DisplayName("✔ 01 - Deve cadastrar um novo usuário com sucesso")
	void deveCadastrarUsuario() {

		// Given
		Usuario usuario = TestBuilder.criarUsuario(null, "Paulo Antunes", "paulo_antunes@email.com.br", "12345678");

		// When
		HttpEntity<Usuario> requisicao = new HttpEntity<>(usuario);
		ResponseEntity<Usuario> resposta = testRestTemplate.exchange(BASE_URL + "/cadastrar", HttpMethod.POST,
				requisicao, Usuario.class);

		// Then
		assertEquals(HttpStatus.CREATED, resposta.getStatusCode());
		assertNotNull(resposta.getBody());
	}

	@Test
	@DisplayName("✔ 02 - Não deve permitir a duplicação do usuário")
	void naoDeveDuplicarUsuario() {

		// Given
		Usuario usuario = TestBuilder.criarUsuario(null, "Maria da Silva", "maria_silva@email.com.br", "12345678");
		usuarioService.cadastrarUsuario(usuario);

		// When
		HttpEntity<Usuario> requisicao = new HttpEntity<>(usuario);
		ResponseEntity<Usuario> resposta = testRestTemplate.exchange(BASE_URL + "/cadastrar", HttpMethod.POST,
				requisicao, Usuario.class);

		// Then
		assertEquals(HttpStatus.BAD_REQUEST, resposta.getStatusCode());
		assertNull(resposta.getBody());
	}

	@Test
	@DisplayName("✔ 03 - Deve atualizar os dados de um usuário com sucesso")
	void deveAtualizarUmUsuario() {

		// Given
		Usuario usuario = TestBuilder.criarUsuario(null, "Juliana Andrews", "ju_andrews@email.com.br", "12345678");
		Optional<Usuario> cadastrado = usuarioService.cadastrarUsuario(usuario);

		Usuario usuarioUpdate = TestBuilder.criarUsuario(cadastrado.get().getId(), "Juliana Ramos",
				"ju_ramos@email.com.br", "12345678");

		// When
		HttpEntity<Usuario> requisicao = JwtHelper.criarRequisicaoComToken(usuarioUpdate, token);
		ResponseEntity<Usuario> resposta = testRestTemplate.exchange(BASE_URL + "/atualizar", HttpMethod.PUT,
				requisicao, Usuario.class);

		// Then
		assertEquals(HttpStatus.OK, resposta.getStatusCode());
		assertNotNull(resposta.getBody());
	}

	@Test
	@DisplayName("✔ 04 - Deve listar todos os usuários com sucesso")
	void deveListarTodosUsuarios() {
		
		// Given
		usuarioService.cadastrarUsuario(TestBuilder.criarUsuario(null, "Ana Marques", 
				"ana_marques@email.com.br", "12345678"));
		usuarioService.cadastrarUsuario(TestBuilder.criarUsuario(null, "Carlos Moura", 
				"carlos_moura@email.com.br", "12345678"));
		
		// When
		HttpEntity<Void> requisicao = JwtHelper.criarRequisicaoComToken(token);
		ResponseEntity<Usuario[]> resposta = testRestTemplate.exchange(
				BASE_URL + "/all", HttpMethod.GET, requisicao, Usuario[].class);
		
		// Then
		assertEquals(HttpStatus.OK, resposta.getStatusCode());
		assertNotNull(resposta.getBody());
	}

}

<h2>✔ Boas práticas</h2>



1. **Mantenha testes pequenos e objetivos:** testes concisos facilitam a identificação de problemas e tornam a manutenção mais simples.
2. **Garanta que sejam rápidos:** testes lentos dificultam a execução frequente, por isso, mantenha-os ágeis para integrar ao fluxo contínuo de desenvolvimento.
3. **Sejam determinísticos:** testes devem sempre produzir o mesmo resultado, evitando dependências externas instáveis que possam causar falhas intermitentes.
4. **Devem ser independentes entre si:** cada teste deve ser isolado, garantindo que falhas em um não afetem outros testes.
5. **Use nomes descritivos:** facilite a leitura com nomes claros e padronizados, como *deve[Comportamento]Quando[Cenário]*, para entender o propósito sem abrir o código.
6. **Inclua poucas asserções por teste:** foque em validar um comportamento por teste para identificar facilmente onde está o problema.
7. **Analise os resultados após cada execução:** investigue rapidamente as falhas para manter a qualidade e a confiabilidade do código.
8. **Mantenha os testes atualizados:** acompanhe as alterações no código para evitar testes obsoletos ou inválidos.
